## Grant catalog v1 (`database-grant-catalog`)

| Role | Kind | Contract |
|---|---|---|
| `opshub_schema_owner` | NOLOGIN group | Owns every migrated schema and object. Has `CREATE` on the database. Not superuser, not BYPASSRLS, no CREATEROLE or CREATEDB. |
| `opshub_runtime` | NOLOGIN group | `CONNECT` and `TEMPORARY` on the database. `USAGE` on schema `opshub` (from 0001). Everything else only through explicit per-object grants in reviewed migrations. No default privileges. |
| Migrator login | LOGIN, per environment | `CONNECT` on the database. Member of `opshub_schema_owner` **WITH INHERIT FALSE, SET TRUE**, so it can do nothing as the owner until the runner's `SET ROLE`. Never a superuser, and cannot reach one through membership. |
| Runtime login | LOGIN, per environment | Member of `opshub_runtime`. Neither it nor anything it can reach is a superuser, BYPASSRLS, CREATEROLE, CREATEDB, `pg_execute_server_program`, `pg_read_server_files`, `pg_write_server_files` or the schema owner. |

Provisioning is the privileged step outside migrations. It creates the roles and the database (owned by an administrator, not the migrator), writes the identity marker, and grants database-level privileges. `src/testing/provision.ts` is the synthetic local implementation. Production provisioning belongs to later infrastructure work.

## Target identity guard

- **Marker.** Database-level settings `opshub.environment` (label `^[a-z][a-z0-9-]{0,62}$`) and `opshub.database_id` (a UUID). Provisioning writes them with `ALTER DATABASE … SET`.
- **Reading.** The guard reads them from `pg_db_role_setting` (`setrole = 0`), never from `current_setting()`, so a session `SET` or a connection `options` value cannot spoof them.
- **Execution.** `readTargetFacts(client)` reads every fact in one `READ ONLY` transaction on the **same connection** that later runs DDL. `assertTarget(expected, facts)` is pure and throws the first violation in this order:

| Order | Code | Condition |
|---|---|---|
| 0 | `TARGET_INVALID_EXPECTATION` | The expected database, environment or database id is malformed |
| 1 | `TARGET_WRONG_SERVER_MAJOR` | `server_version_num / 10000 ≠ 17` |
| 2 | `TARGET_WRONG_DATABASE` | `current_database()` differs from the expected name |
| 3 | `TARGET_IDENTITY_MISSING` | Either marker is absent |
| 4 | `TARGET_WRONG_ENVIRONMENT` | The marker environment differs from the expected one |
| 5 | `TARGET_WRONG_DATABASE_ID` | The marker database id differs from the expected one |
| 6 | `ROLE_MISSING` | `opshub_schema_owner` or `opshub_runtime` does not exist |
| 7 | `ROLE_MIGRATOR_IS_SUPERUSER` | `session_user` is a superuser, or can reach one through membership |
| 8 | `ROLE_MIGRATOR_NOT_OWNER_MEMBER` | `session_user` cannot `SET ROLE opshub_schema_owner` |
| 9 | `ROLE_RUNTIME_PRIVILEGED` | `opshub_runtime`, or any transitive member, can reach an elevated role or the schema owner |

## Migration protocol

`migrate({ connection, expected, migrationsDir?, lockTimeoutMs? }) → { applied: {version, name, sha256}[], alreadyApplied }`

1. **Files.** `loadMigrations(dir)` accepts only `NNNN_slug.sql` (four digits, lowercase snake_case) regular files with at least one statement, numbered 1..N without gaps. The checksum is SHA-256 of the exact bytes; checkouts are LF-only under `.gitattributes`. Anything else fails before connecting:
   - `MIGRATION_BAD_FILENAME`: a down file, a README, an unpadded or uppercase name, or a subdirectory.
   - `MIGRATION_EMPTY`
   - `MIGRATION_SEQUENCE_GAP`
   - `MIGRATION_DUPLICATE_VERSION`
2. **Guard.** As above. A rejection happens before any DDL.
3. **Serialize.** Session advisory lock `pg_advisory_lock(0x4f505348, 0x4d494752)` (`MIGRATION_LOCK_KEY`) with `lock_timeout = lockTimeoutMs`, default 30 s. If another runner holds it past the timeout, the run fails with `MIGRATION_LOCK_TIMEOUT`. The lock is released when the connection closes, including after a failure.
4. **Session.** `SET ROLE opshub_schema_owner`, then `SET search_path = ''`. **Every object in a migration must be schema-qualified.** An unqualified create fails with SQLSTATE 3F000.
5. **History.** `opshub_migration.applied_migrations(version int PK, name text, sha256 char(64), applied_at timestamptz default now(), applied_by text default session_user)`. It is owned by the schema owner, with no grants to PUBLIC or runtime. The runner creates it only when it is absent, so a run with nothing pending issues **no DDL**.
6. **Verify history.** History must be exactly the files' prefix:
   - `MIGRATION_UNKNOWN_APPLIED`: history is ahead of the files.
   - `MIGRATION_NAME_MISMATCH`: an applied file was renamed.
   - `MIGRATION_CHECKSUM_MISMATCH`: an applied file was edited.
7. **Apply.** Each pending file runs in its own transaction together with its history row.
   - **Failure:** the run fails with `MIGRATION_FAILED`, detail `{version, name, sqlState}`. The server message stays on `cause` only, because it can quote row values. That migration rolls back completely; earlier ones stay committed.
   - **Transaction escape:** a file that ends the transaction (for example `COMMIT`) is detected through `pg_current_xact_id()` and fails with `MIGRATION_TRANSACTION_ESCAPED`. Its escaped statements may already be committed, so migrations must not contain transaction control.
   - **Not supported:** statements that cannot run inside a transaction block, such as `CREATE INDEX CONCURRENTLY`.
8. **Forward repair only.** Fix an unapplied failed file in place, or add the next version. Never edit or delete an applied file, never write a down migration, and never auto-sync a schema.

## Runtime access and unit of work

- `createRuntimeDb<DB>(poolConfig): Kysely<DB>` connects as a runtime login. `DB` is the consuming module's table interface; this boundary defines none.
- `withUnitOfWork(db, work)` is one database transaction. It commits when `work` resolves. When `work` throws, or hits a database error such as SQLSTATE 23505, it rolls back and rethrows the original error, and **no row persists**.
- No provider or object-store I/O may run inside `work` (04-data-architecture).
- Tenant context, RLS and transaction-local `merchant_id` settings are not part of v1. T0006 and the tenancy tasks own them.

  - The installed tree equals the pins.
  - The only allocated migration is `0001`.

## Errors (harness assertion → meaning)

| Assertion | Meaning |
|---|---|
| `direct dependencies differ from the qualified stack` / `lockfile resolves … differently` / `installed … differs from the pin` | Pin or lockfile drift, or a stale `npm ci` |
| `disposable PostgreSQL image is not the digest-pinned 17.11 image` | The container route changed without a contract revision |
| `unexpected migration allocation` / `0001 must not create tenant or domain tables` | A migration was added or changed outside the migration-order lock |
| `Docker engine not reachable` | The disposable route is unavailable. Start Docker; the result is not a pass |
| a named Vitest test is not `passed` | A guard, protocol, role or unit-of-work behavior regressed |

## Tenant and transaction assumptions

- No tenant data, and no tenant or domain tables.
- Fixtures are synthetic: generated database and role names, random per-run passwords that are never logged, and a test-only probe table created in test setup.
- Each migration is one transaction, and each unit of work is one transaction. No external I/O happens inside either.

## Not qualified here

- **Platforms:** Linux and CI runners. Only Windows 10 x64 with Docker Desktop 29.6.2 (Linux engine) was executed.
- **Disposable route:** a non-Docker disposable PostgreSQL.
- **Production operations:** production provisioning, the release migration job, credentials and secret handling, and backup or restore.
- **Migration content:** non-transactional migrations, RLS and tenant context, and pg-boss schema and grants.

## Changing this contract

- Changing a pin, the image, the guard order or codes, the protocol, the history table or the role semantics needs C-T0003-v2 under `boundary:database`, with the harness rerun and its evidence recorded.
- Adding roles needs `database-grant-catalog`.
- Adding migrations needs `database-migration-order` and an owner-assigned version.
