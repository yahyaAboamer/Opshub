# OpsHub — concrete MVP technology selection

**Recommendations for human review**, chosen after the technology-independent boundaries in 01–14. Current official documentation was consulted on14 October 2026; exact supported patches/hosting plan/package compatibility are checked and pinned in a later authorized implementation. No dependencies or infrastructure are installed here. [ADR001–ADR011](adr/ADR-001-architecture-style.md) capture the significant decisions.

| Area | Recommendation / alternatives considered | Reason, trade-off and exit path |
|---|---|---|
| Web UI/build | React + TypeScript + Vite; alternatives Next.js full-stack or Django server templates | Authenticated queues/forms/analytics do not need SSR/SEO. Static bundle plus same-origin API has explicit session/authority behavior and one release. More client routing/state plumbing than server templates; generated DTO client and accessible component discipline help agents. Frontend can later change without business/provider rewrite. [Vite](https://vite.dev/guide/), [Next docs](https://nextjs.org/docs) |
| Backend | NestJS + TypeScript on Node 24 LTS, standard Express adapter; alternatives plain Fastify, Next application actions, Django/Python | Modules/DI/controllers/guards give small team and agents clear ownership; same language across interfaces. More conventions/decorators than Fastify; avoid elaborate decorators/metaprogramming/CQRS library. Express is selected for middleware/session/raw-body compatibility rather than synthetic speed. Django is credible if team skill strongly favors Python, but adds cross-language DTO work. Keep domain functions/provider ports framework-independent. [Nest](https://docs.nestjs.com/first-steps), [modules](https://docs.nestjs.com/modules), [adapters](https://docs.nestjs.com/techniques/performance), [Django](https://docs.djangoproject.com/en/5.2/), [Node 24 LTS](https://nodejs.org/en/blog/release/v24.11.0) |
| Primary database | PostgreSQL 17, paid managed instance; alternatives MySQL, document DB or hosted DB with integrated auth | Relational constraints, locks, transactions, RLS and SQL projection needs align directly.17 is a deliberate supported baseline, not claimed newest release; verify hosting availability/current security patch. JSONB retains bounded evidence without replacing relational identities. SQL/pg_dump portability is the exit path; RLS remains Postgres-specific. [RLS docs](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) |
| Query/schema layer | Kysely + `pg` with reviewed explicit SQL migrations later; alternatives Prisma, Drizzle or raw SQL only | Typed SQL preserves composite constraints, explicit transaction-local tenant context/locks and contributor queries. Less generated relationship convenience than Prisma; team must own migrations/types. Do not mix two ORMs or auto-sync schema. Exit via plain SQL/driver; no domain business logic in ORM hooks. [Kysely](https://kysely.dev/) |
| Authentication | Auth0 managed OIDC/hosted login; local OpsHub sessions/roles; alternatives Supabase Auth or self-hosted auth/Keycloak | Avoid password/recovery/MFA ownership while preserving portable issuer/subject binding and local authority. External outage/pricing/MFA plan gates; use standard OIDC port and separate local User ID. No Auth0 Organizations dependency for tenant isolation. Supabase is viable but not needed as direct browser DB/BaaS; self-hosting raises ops burden. [Auth0](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow-with-pkce/add-login-using-the-authorization-code-flow-with-pkce), [Supabase Auth](https://supabase.com/docs/guides/auth) |
| Background jobs | pg-boss in existing PostgreSQL with same-transaction enqueue; alternatives Redis/BullMQ or managed queue | Durable work/scheduling without another datastore. Shares DB capacity and library has maintenance dependency; versioned PII-free envelopes and authoritative action/run/checkpoint records permit a later reviewed queue change. No claimed exactly-once external effect. [pg-boss](https://github.com/timgit/pg-boss) |
| Cache | No external cache; tenant-safe request/local client state and projection tables | Avoid cache invalidation/permission leaks and extra service. Add scoped Redis only after measured latency/rate need; never put credentials/PII in generic keys |
| Files/recovery journal | Private Amazon S3; alternatives hosting disk or S3-compatible store | Persistent independent files/backups and conditional immutable dispatch markers. Additional AWS permissions/key/region management and journal availability dependency; normal files use storage port, but replacement store must match required conditional/recovery semantics. Ephemeral app disk is unsuitable. [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [presigned access](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html) |
| Deployment | Paid Render web + worker + Postgres; alternatives Railway or AWS managed/container stack | Explicit background-process and recovery-capable relational hosting fits small-team topology; no Kubernetes/infra fleet. Region/plan/egress/residency and external auth/storage remain review gates. Railway is credible, including Gentry's historical hostname, but that observation does not decide OpsHub's host. Docker image/Postgres/standard OIDC+storage ports provide exit path. [Render services](https://render.com/docs/service-types), [backups](https://render.com/docs/postgresql-backups), [Railway Postgres](https://docs.railway.com/guides/postgresql) |
| Observability | Hosting structured redacted logs + Sentry errors/selected traces + OpenTelemetry correlation + DB business-health projection; alternatives full managed observability or self-hosted Prometheus/Grafana | Enough to diagnose source/job/action problems without operating a monitoring stack. Must review PII defaults/retention and bound ingestion costs. Export OTEL spans/log data through ports; no required standalone collector initially. [OTEL](https://opentelemetry.io/docs/concepts/signals/) |
| Email | Resend for invitations/account support messages; alternatives SES or IdP-only invitation delivery | One small transactional mail integration, stable invitation/message identity and suppressed resends. Sending email does not activate membership; wrong/expired token remains denied. No merchant-customer outreach. Hosted IdP supplies its own login/recovery messages. Provider retention/deliverability/cost review; SMTP/API port makes replacement possible. [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys) |
| Testing | Vitest + real PostgreSQL/Testcontainers + mock provider server + Playwright; alternatives Jest or provider-only smoke tests | Deterministic domain/concurrency/tenant/effect/analytics proofs plus real user/API journeys. Container/runtime/decorator compatibility must be confirmed on pinned toolchain; local equivalent disposable DB where Docker unavailable. [Vitest](https://vitest.dev/guide/), [Testcontainers](https://node.testcontainers.org/modules/postgresql/), [Playwright](https://playwright.dev/docs/api-testing) |

## Why this combination

One TypeScript codebase, ordinary HTTP, explicit SQL and one primary transaction system suit AI-assisted implementation: modules own data/capabilities, guards are reviewable, migrations remain human-reviewed and tests check effects rather than mirrored code. Type safety assists editing but cannot replace runtime validation, server authorization or DB constraints. The design accepts a few managed utilities rather than operating password/email/storage/monitoring infrastructure. Per-tenant authorization remains portable local application logic.

Keep runtime/module/provider/deployment boundaries ordinary and small. Do not introduce a generic DDD framework, event-sourcing platform, GraphQL product layer, tRPC in addition to REST, service mesh, warehouse, AI runtime/LLM agent inside the product or advanced billing. No AI API key is required; “maintainable by AI coding agents” describes the development workflow, not a new product feature.

## Remaining stack gates

Confirm Auth0 plan supports intended MFA/step-up and account economics; Render region/Postgres major/backup recovery suitability; S3 protected journal/key permissions; Nest/Vitest TypeScript decorator transformation; pg-boss migration/grant compatibility; Sentry scrubbing defaults and data location. These are specific technical qualifications, not uncertainty about every choice. If a gate fails, revise the corresponding ADR with evidence. No precise cloud bill, uptime/latency or provider success guarantee is inferred from documentation.
