# OpsHub — deployment, environments and recovery

**Recommendation:** one paid Render web service serving built merchant/platform React bundles and Nest API, one worker from the same immutable image, one paid private PostgreSQL 17 database, private Amazon S3 storage and managed identity/email/error monitoring. [ADR009](adr/ADR-009-deployment.md). This is a proposal; no account, infrastructure, deployment or secret is created here.

## Environment isolation

| Environment | Contract |
|---|---|
| Local | Same database major with real runtime roles/RLS, local worker/queue and synthetic fixtures. Provider mocks; no production secrets/raw customer data. Docker optional where available; equivalent disposable test DB possible |
| Test/CI | Disposable real PostgreSQL with nonowner role tests and fake provider clocks/failures; egress to production provider APIs denied. Short-lived object/mock endpoints and isolated auth stub |
| Staging | Independent database/storage/auth app/provider sandbox or explicitly controlled pilot credentials; mutation egress disabled by default. No production data copy without separate redaction/authorization |
| Production | Dedicated project/workspace/secrets/storage namespace/database; paid restore-capable services, verified connection ownership and reviewed release configuration |
| Preview | Optional short-lived application plus disposable synthetic DB/mocks; no live provider credentials/webhook registrations or shared staging writes. Defer if cost/isolation outweighs benefit |

Use private database address and disable public DB access except explicit temporary reviewed operator need. Web and worker have separate secrets/grants; migration/backup credentials live only in controlled release/operations context. Database grants distinguish tenant runtime, control plane, worker, queue transport, retention and schema owner. Web holds no provider decryption key. Secret rotation/version recovery is documented; encrypted backups without the required protected decryption keys are not recoverable evidence.

[Render service types](https://render.com/docs/service-types) supports background workers and paid Postgres recovery; [private networking](https://render.com/docs/private-network). Region/data residency/latency/plan suitability remain A06/A05, not assumed Cairo hosting. Use established HTTP runtime/image and static asset serving; no serverless timeout dependency for background workflows.

## Release and schema changes

Later authorized implementation uses pinned image/lockfile and compatible web/worker release versions. Controlled one-off migration job takes a release lock, uses schema-owner credentials, verifies target environment/database, and applies reviewed expand/contract changes. Runtime never runs schema synchronization. Deploy compatible expansion before app, delay destructive contraction until approved rollback window/data checks. No production migrations are generated in Phase 4.

Graceful worker shutdown stops accepting dispatch, finishes bounded safe work and records uncertain mutations conservatively. Rolling deploy cannot reclaim expired write leases and resend. A release rollback restores the compatible prior application image; it cannot undo external effects or destructively down-migrate evidence. For incompatible schema/provider failure, stop mutation starts and forward-fix under review while preserving reads/reconciliation. Readiness probes inspect DB/worker protocol versions; provider outage is displayed per capability rather than crashing all reads.

## Backup and restore

Paid Render Postgres currently documents PITR with a plan-dependent window; Free compute lacks that recovery. Select a purchased plan that meets reviewed recovery needs, not a free pilot default. [Recovery documentation](https://render.com/docs/postgresql-backups). Proposed additional encrypted logical exports to private independent storage, object versioning/lifecycle and protected credential-key backup improve recoverability; cadence/retention/RPO/RTO require A06/OP12 approval and actual restore measurement. Do not invent a measured recovery guarantee.

Restore drills use a **new isolated database**, user-access-and-mutation-egress-off runtime, synthetic/redacted data handling and no customer messages. Check identity/grants/RLS/FKs, canonical relationships, source assertions/corrections, open action reservations/results, queue/domain-run checkpoints, projection revisions, file integrity and secret key availability. Independently retained privacy manifests must be replayed before user access. Backup contains jobs, but restoring jobs is not authorization to replay external writes.

## Protecting external effects across backup rollback

A database restore can forget an external effect that happened after the restore point. Keep a minimal **independent recovery journal in the already-required private object store**, separate from DB backup rollback. Record before provider dispatch, before releasing Admin manual fallback, and before issuing an external-contact start reservation. Confirm durable creation before releasing that path. Storage failure/uncertainty blocks issuance; marker presence means **may have executed**, not success or an actual call. Results/no-call evidence are appended separately. These bounded record types protect irreversible effects and contact allowance; they are not a general event-sourcing system.

The versioned recovery envelope includes environment/recovery protocol, merchant, action/case/intent/effect/attempt IDs, exact **operation/effect kind and business reservation scope**, verified provider-account namespace/native account ID, stable native subject bindings where available, canonical subject IDs, original/replacement/dependency relationships and known native result IDs, intent hash and reviewed authority reference. Contact markers additionally identify canonical case/purpose/objective and held ordinal; handovers identify the same effect scope and responsible Admin. Local UUIDs/hash alone are insufficient. Store no customer contact body or credential; encrypt any minimally necessary protected recovery context under reviewed policy. A rediscovered native subject is reconciled to this descriptor rather than receiving an unconnected executable objective. Missing reliable binding cannot be filled by phone/name guess.

Use restricted append/read recovery permissions, environment-separated prefix, conditional-create enforcement and tested version/deletion protection. Runtime has no journal deletion/version-deletion permission; controlled retention cannot remove a needed reservation/coverage record. Conditional S3 writes prevent overwriting an existing marker; they do not make S3+Postgres+provider an atomic transaction. [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html). Preserve schema versions, recorder release/version, complete paginated enumeration and independently retained coverage/checkpoint manifests. Retention covers every allowed backup restore horizon plus execution/reconciliation margin, and all unresolved holds; a journal gap or unreadable newer schema blocks recovery. The proposed 24-month boundary in 11 is subordinate to these minimum safety/policy requirements.

After restore, deny product user reads/exports/writes and all merchant mutation egress. Quarantine every restored approved/started/handed-over effect and contact allowance that may predate missing history. Enumerate the complete independent journal and qualified provider/source changes over the recovery gap; rebuild missing holds from recoverable business scope and reconcile positive identities. Missing subject/connection/descriptor/coverage quarantines the **whole affected merchant/connection**, not an invented narrow reservation. Restore-created jobs cannot release these holds. Imported provider objects without known approval stay source-reported discrepancies, not retroactively authorized effects.

No automatic mutation/contact resume until restored holds, independent coverage, current authority and qualified evidence agree. Unprovable no-effect keeps the relevant objective blocked and escalated; do not reset it because the restored database calls it Approved. Independent provider/phone activity remains outside OpsHub's control; A01's booking ownership plus reconciliation still apply. Each enabled core action must demonstrate its ambiguous-result investigation/positive-match route and accountable Admin/provider escalation; a happy-path round trip alone is insufficient. If no safe resolution can be established, the case remains blocked under an explicitly reviewed exception, not blind retry. This is an A02 feasibility/release risk. The runbook is a design contract, not executed recovery.

## Restored authority and privacy access gate

Use a new recovery epoch enforced from protected runtime configuration **outside the restored database**. All restored sessions and invitations are invalid; fresh OIDC login establishes identity only. Treat restored merchant memberships/platform assignments, service restrictions and connection ownership as provisional. For the modest pilot, use audited revalidation through OP02's independently verified merchant representative and currently authorized infrastructure/platform recovery procedure. Do not trust the restored Admin grant to authorize its own recertification or permit platform self-grant. A complete independently retained revocation record may support revalidation if available, but a second generic security ledger is not required. Until current grants/service restrictions are verified, deny user reads and exports as well as mutations.

Store authorized/completed/cancelled privacy disposition manifests in a separately protected object prefix outside DB rollback, with version, tenant/source/native target scope, policy/authority references, effective time and no unnecessary customer text. Record durable authorization before destructive processing and completion after it; uncertain/partial stages are reconciled or reapplied idempotently under approved policy. Coverage/retention must span every restorable backup and unresolved request, not just the older DB's list. Missing privacy coverage keeps affected data inaccessible. Replay approved deletions/redactions across database, derived snapshots and objects before reopening; never restore an older backup into ordinary access without these records. Exact disclosure/erasure/hold policy remains A05, and protected identifiers remain personal-reference data rather than claimed anonymization.

Reopen access per merchant only after grant/service/connection verification and privacy replay pass. Operational reads may resume while specific provider/contact holds remain visible, but affected action/call starts stay blocked. Record the recovery decision and current epoch without inventing a lost historical actor/result. 14 tests post-backup revocation, consumed invitation, redaction, lost objective, handover and contact budget. No recovery operation occurs in Phase 4.
