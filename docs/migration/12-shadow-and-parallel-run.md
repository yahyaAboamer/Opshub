# Shadow mode, controlled actions and parallel operation


## Cross-class authority conflicts

The authority ledger includes a source-qualified **conflict/dependency matrix**, not only a list of class owners. Default conservative proposal pending MD08/MD10:

| Overlapping business scope | Gate during parallel/gradual transfer |
|---|---|
| Booking ↔ same-Order cancellation | One reviewed coordinator/authority or verified hold of the competing path until first effect settles and policy revalidates |
| Replacement creation ↔ original-order cancellation/booking or another recovery objective | Serialize reviewed original/new dependencies and exact eligible scope; compatible later steps require explicit policy/result evidence, never independent concurrent decisions |
| Replacement creation ↔ native/provider automatic booking | Transfer/disable coupled paths together or exclude native automation with verified evidence; no two bookings |
| Material recipient/items/commercial/consent edits ↔ unstarted approval/contact/action | Version/dependency check invalidates stale approval; started effects and disputed contact scope remain held |
| Annotation ↔ automation-triggering behavior | No low-risk annotation stage until qualified trigger/side-effect behavior is known and contained |

Different classes may have different owners only where their eligible scopes are proven nonoverlapping/nonconflicting. Where Gentry/manual actors cannot consume a shared authoritative hold, use an operationally verified stop for the conflicting incumbent scope or transfer that connected conflict group together. An unenforceable ledger declaration is not a safe control. No new distributed locking service is selected.

Shadow/limited-action exit additionally requires MP-SEED01 coverage, IM05 repair proof, MP-ACQ01 capture closure, privacy replay suppression and KR18–KR21 temporal/quality tests. Validate EA23 races and actual native result counts before widening class flags.
**Default first production validation stage: shadow mode.** This is a future rollout design, not authorization to connect accounts or activate production. [OD08/OD09](../product/00-owner-decisions.md) integrated core/Product/ROAS remain MVP requirements.

## Shadow capability contract

One pilot merchant ingests authorized real Shopify/Bosta/applicable Meta evidence into validated read state, computes operational queues/statuses/KPIs and compares against Gentry/current merchant process. **OpsHub consequential external mutations and contact starts remain disabled** at server/worker/provider-egress boundary, not just UI. Observed incumbent calls/actions may be imported with evidence; OpsHub does not initiate an additional call or replay an old task.

Read-only synchronization/ingestion/reconciliation and source refresh have bounded credentials/budgets, truthful coverage and account ownership. Queue attention is explicitly shadow advisory, not a new action authority. Provider webhook registrations/configuration changes require later authorized setup and qualification; Phase 5 performs none.

## Shadow record and daily comparison

Record merchant/source snapshots/cutoffs/coverage, pipeline/mapping/policy/golden versions, actual run/generation, identity/collision/disposition totals, per-queue member set and reason, source freshness/performance, KPI numerator/denominator/exclusion sets, Product/spend/revenue allocations, incumbent actions/new provider results, discrepancy IDs and private evidence references.

Investigate false identity matches, missing current work, duplicated objects, unknown finality/collection, stale data/partial periods and definition differences. Classify each OR comparison exact/explained/untrusted; never use Gentry action completion or paid→Collected as a truth shortcut. A source sync “healthy” label is insufficient without complete pagination and stable bindings.

## Exit criteria — MD11/MD13 approval

- Approved pilot account ownership, MD01 source authority, MD02 history/dependency scope, relevant launch policies and full row/object accounting.
- Zero unexplained identity collisions/cross-tenant links, contributor mismatches, silently dropped records or unsafe latent dispatch paths. Unknown historical observations are enumerated with containment/owner; no blocking day-one work omitted.
- Initial acquisition plus replay and incremental updates pass per source; ordering/duplicate/read outage recovery demonstrated; actual coverage/freshness/export performance meet approved measured targets.
- Representative delivered/RTO/pending/unknown, confirmation/reach/action-required, physical/payment pickup, return/replacement and spend/revision cases have trusted expected results. Rare cases may use controlled synthetic qualification; report which are not observed in production.
- Observe relevant cohort/calendar boundaries, repeat reporting windows and a source degradation/recovery interval; resolve discrepancies and retain reviewed examples. Calendar/late-revision tails determine duration; a quiet period is not proof of safety.
- All required synthetic KPI/domain/isolation tests and restore/action safety contracts pass in controlled implementation. Provider action qualification includes ambiguous-result path before that class enables.
- Named responsible Admin/operator training, kill switch, monitoring/escalation, exclusive incumbent/target action ownership and a rehearsed cutover/rollback plan.

No invented accuracy percentage or fixed number of shadow days. MD11 selects calendar duration and minimum representative observations after measuring arrival mix, coverage and delays. Unknown unprovable effect/critical identity can block its class or launch; a blanket “accepted discrepancies” sign-off cannot waive correctness.

## Controlled action pilot ordering

| Stage | Enabled scope / risk justification | Required pass evidence |
|---|---|---|
| SH0 | Read-only sync, computations and shadow comparison | Source/identity/KPI/privacy/tenant gates |
| SH1 | One bounded low-risk annotation class, only if qualified to preserve other data and trigger no notification/automation | PC-S08/EA/restore gates, current Admin, native result lookup; skip this class if no useful safe scope |
| SH2 | Limited single-outbound Bosta booking for one qualified purpose/merchant | PC-B01–B06/B09–B11; native auto-booking excluded, old scopes reconciled, physical/commercial scope separately authorized |
| SH3 | Replacement-order creation + explicit required annotation/booking effects | PC-S07/S08/S10; pricing/payment/consent policy, partial-success recovery and native connector checks; never recreate after booking failure |
| SH4 | Eligible Shopify cancellation | PC-S06/S09/S10; irreversible financial/inventory/notification consequences qualified and Admin-reviewed |

Risk increases from read state to bounded metadata, physical consignment, new commercial object/multieffect sequence and irreversible cancellation. If provider evidence contradicts this ordering, MD10 chooses a safer sequence or leaves the affected capability unavailable. A required core capability still must qualify before integrated MVP release; indefinite manual core is not acceptance.

Flags are per environment/merchant/provider/account/**action class**, default off; support disabled/read-only/shadow/limited/enabled states, reviewed limit/eligible scope/configuration version and emergency disable. Global enable is insufficient. Every class has qualified contract, current authority, explicit side effects/limits, positive/unknown recovery, independent marker coverage, monitor, responsible Admin and disable/rollback path. Lowering a flag blocks new starts but cannot retract a sent request.

## Parallel run authority

Keep Gentry/incumbent process for a bounded comparison period while OpsHub reads/computes. Maintain a signed **authority ledger per merchant/provider/account/action class**, including native connector and manual executor:

- In shadow: incumbent is sole mutation/contact authority; OpsHub off.
- During transition: all starts for the switching class held, old paths drained/settled, journal/native inventory reconciled.
- After class switch: OpsHub is sole normal authority; Gentry/manual/native auto-booking path disabled or explicitly nonexecuting for that class.
- Safe fallback uses the same OpsHub objective/known-no-effect handover token; it is not a second autonomous process.

Booking and replacement creation are coupled where Shopify creation triggers native booking; never switch them independently without proving excluded automation. Incumbent observations/results remain compared; duplicate independent provider activity is a discrepancy, not assumed impossible under local locks.

Compare named queues, canonical identity/coverage, source assertions, KPI contributors/product/spend/revenue and case obligations. MD11 defines maximum parallel duration/review cadence, dependency/late-revision completion and archive owner. Exit only after cutover gates and discrepancies/holds are accounted for. If authority cannot be verified exclusive, hold that class; both systems must never independently book the same shipment. [13](13-cutover-and-rollback.md).
