## Review

A security self-review used the approved `differential-review` skill; the report is in the session scratchpad. The diff is greenfield, so the skill's baseline and git-history phases don't apply, and a focused adversarial pass was done on the guard, the runner, migration 0001 and provisioning. Findings:

- **F1 (HIGH), fixed.** The role check followed membership only downward. A runtime login or migrator granted a superuser or BYPASSRLS role could `SET ROLE` upward while the guard passed. Fix: upward reach CTEs for the runtime role's members and for the session user, plus the server file/program roles. Two tests added.
- **F2 (MEDIUM), fixed.** A connection `options` value could set `search_path` for migrations. Fix: the runner sets `search_path = ''`, and migrations must schema-qualify. One test added.
- **Accepted and recorded in the contract.** F3: a migration file can still change its role or escape its transaction; escape is detected after the fact. F4: whoever owns the database (the administrator) can change the identity marker. F5: server messages stay on `cause`. F6: `reset lock_timeout` in `finally` can mask the original error if the connection dies.

## Findings for consumers

1. **Every migrated object must be schema-qualified.** The runner pins `search_path = ''`.
2. **Grant to `opshub_runtime` per object, explicitly.** There are no default privileges, and the runtime role has only `USAGE` on `opshub`.
3. **Ownership.** Migrations run as `opshub_schema_owner`, so objects are never owned by a login. The migrator login is a member with `INHERIT FALSE`.
4. **No transaction control in migrations.** That includes `CREATE INDEX CONCURRENTLY`.
5. **Provisioning writes the identity marker,** and the guard reads it from the catalog. A database without it can never be migrated.
