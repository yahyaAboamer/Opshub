# Task execution protocol

Every implementing agent or session (Claude Code, Codex or another) uses the same canonical manifest, exact task/spec reading set and accepted main. The repository's canonical implementation files are sufficient for normal execution; external guidance conversations are advisory only and are never a task dependency or a source of authorization. One Task ID is one bounded scope with one active claim. No two active claims may own the same ID or overlapping editable boundary/shared lock. Manifest/status/claim/lock changes are made one at a time, as the human owner directs; no agent claims a Task ID or shared lock the owner has not assigned to it.

Roles: the human owner assigns Task IDs, allocates shared locks and migration order, accepts tasks and approves merges by default. No permanent separate integration owner or independent reviewer is assumed. Where a task file, the manifest, the Definition of Done, parallel-safety or a generated view says "integration owner", read it as the human owner (or whoever the owner explicitly delegates for that task). Where a task's acceptance says "independent review", it is the owner's review, optionally informed by a separate fresh review session. A fresh review session may be used when a task or gate explicitly requires review, or when high-risk work (migrations, RLS/auth, provider/action/recovery protocols) benefits from independent context. This rule does not change decision-gates.yaml: a gate that names a reviewer, signer or other decision maker keeps that requirement and its recorded verdict; the owner designates who performs it.

One worktree/branch per task: codex/tNNNN-scope or claude/tNNNN-scope, based on current accepted main. Inspect existing work before editing. A task branch owns only its listed areas and one allocated migration if applicable. Shared package/lockfile/DTO/provider-port/action/recovery protocol, grants and router changes require an explicit owner-allocated lock and contract review. A fresh session per Task ID is preferred, not mandatory. A session may continue to another explicitly assigned Task ID only after the previous task is accepted and merged, its branch/worktree is cleaned up, main is refreshed, the new task's reading set is reread and context remains reliable. Continuing never blurs Task-ID boundaries.

Predecessors must merge before a consumer starts. Freeze actual produced C-task-v1 boundary with typed interface/schema, errors, scope/transaction assumptions, fixture references and exact commands in docs/contracts. Consumer verifies that accepted artifact; it does not invent neighboring signatures. Contract change invalidates affected downstream readiness and requires current-main update/revalidation.

Parallel agents are optional and used only when the owner explicitly assigns separate nonoverlapping tasks and locks. Parallel candidates after shared predecessors are accepted: T0306 Orders UI with T0401 Bosta read mapping; T0702 required annotation with T0703 booking adapters under frozen engine/ports; T0909 dashboard UI with T0908 ROAS computation. These are possibilities, not simultaneous scheduling instructions. [parallel-safety.json](parallel-safety.json) enumerates exact preconditions/locks. Do not parallelize core migrations/RLS/auth/action/recovery protocol or overlapping route registration.

Task workflow: inspect claim/baseline → validate gates/dependencies → independently fix expected fixture results → implement one boundary → run relevant checks/inspect actual evidence → submit for review (owner, optionally with a fresh review session) → owner accepts and approves the merge → canonical status/digest updated. Update every surviving parallel branch from main after dependency/shared-contract merge and rerun affected integration/tenant/contract checks before acceptance.

Vertical slices: a user-facing task first writes its journey client contract against accepted producer ports (resources/commands, fields, cursor/filters, authorization outcomes, error codes, visible state inventory, stable IDs, expected-version behavior per architecture chapter 08). It then builds UI and its own listed read adapter together and proves the journey in the browser against the running stack at narrow and desktop viewports. A missing producer field or state stops the task with a bounded producer-contract amendment request. Domain rules and consequential commands stay in their producer tasks.

Skill routing: use specialized skills only when relevant to the selected task, choosing the smallest relevant approved set. UI tasks may invoke approved frontend-design, web-design or React skills. PostgreSQL/RLS tasks may invoke the approved Postgres skill. High-risk security or recovery changes may invoke approved review skills. Tests and approved task acceptance criteria remain authoritative; skills never override approved task/specification behavior. Never load unrelated skill packs because they are installed, and treat an unavailable skill as optional, not a blocker.

Human briefings (any agent): before implementing an assigned Task ID, and after its readiness and gates are checked, give a short brief: purpose, why now, layers involved (only those that apply: frontend, backend/API, database, background jobs, auth/security, external providers, infrastructure/deployment), technical scope, expected result, reviewable output, and approved skills selected with a short reason for each (or "No specialized skill selected"). Derive layers and skills from the selected task; task files don't list them. An explicit human assignment of a READY task needs no second confirmation. After the task is recorded ACCEPTED, give a short recap: plain English, layers changed, technical changes, result, validation (PASS/FAIL/NOT_CHECKED), important notes, and next task (the Task IDs now READY in the manifest plus one recommended ID). The detailed implementation-handoff evidence is still required before acceptance. No agent starts a next Task ID until a human explicitly assigns it; a bounded batch is a scope ceiling, not an instruction to auto-advance.

If genuinely blocked, record exact source locator, missing input/decision/environment, affected task IDs, safe completed scope and next responsible role. Keep unrelated eligible work available. No generic retry/relabel closes a safety blocker. Supersede rather than recycle task IDs. Split XL/unbounded discoveries before work.

Completion/resumption uses [execution-state](execution-state.md), which links status authority to the manifest. [single-task](agent-prompts/single-task.md) and [bounded-batch](agent-prompts/bounded-batch.md) are prompts for an explicitly assigned task or set. Local approval never permits provisioning, account messaging, real provider calls, deployment or cutover.
